# Native billing client: truthful activation and account isolation

Local candidate on `codex/readiness-native-billing-client-20260920`, based directly on actual native repository `aa13193b28c552f977fa36a4683bb3a688d3da4f`. Source snapshots and real accounts remain untouched. No purchases, billing provider mutations, upstream push or deployment occurred.

## Reproduced high-severity failures

The actual old `js/billing.js` returned `ok:true` after native receipt success even when every server refresh still said free; a paused A refresh overwrote B's signed-in session; changing accounts during SDK identification still continued to purchase; and an unconfirmed receipt was described as not charged. [Original four-case failure log](evidence/native-billing-client-before.log). `upgrade.html` duplicated the unsafe refresh/write logic, declared payment confirmed from a URL query, and navigated onward after exhausted retries.

## Resolution

- One captured account credential belongs to the entire operation. Every asynchronous continuation checks it before another provider call, local session write, or navigation. Refresh requires the exact same returned app-user ID and a valid tier; a stale or malformed response cannot overwrite another sign-in. A storage failure is not activation success.
- Provider identification, purchase and restore run in one queue. Duplicate purchase/restore requests are blocked while active; a delayed boot identification cannot silently change the SDK account under an active purchase. Explicit SDK cancellation is distinguished from generic errors.
- Native receipt success is pending until the same account's server entitlement is Pro and the replacement credential is saved. Uncertain results never assert that no charge occurred. Pending purchase/restore recovery is stored under that account in sessionStorage and survives reload; a repeated purchase cannot start while it is unresolved. A verified empty restore clears only its own newly-created marker, preserving a preexisting uncertain purchase.
- The upgrade page uses the same refresh implementation. Return-query parameters trigger a plan check, not a payment-success claim. Pending access stays on a recovery screen with reachable Check and Restore controls. Restored Pro access permits navigation. A native build with no billing bridge does not fall through into web Stripe checkout.
- Web checkout retains the same account/plan nonce and return URLs across response-loss retries and reloads, matching the backend's durable attempt contract. Intentional plan changes create a new request. Confirmed completion clears only the current account's marker. `checkout_complete` and `subscription_exists` responses lead to existing-plan recovery. Delayed checkout responses cannot redirect a replacement account.

Existing products, prices, plans, entitlement ID, public SDK key, trial copy and store-management rules are preserved. The billing script cachebuster is updated in both native entry pages. Recovery controls now have 44px touch targets.

This patch targets actual native source, not the C2 checkout. Integrate with the separate native auth candidate `618c613` and packaging changes while preserving both package/test edits. The one-time auth release manifest covers an exact patch: combining commits in one upstream push requires a regenerated, reviewed manifest; do not bypass its scope/hash failure.

Backend checkout attempt/idempotency and RevenueCat transfer/ownership changes are independent product-inventory work. The UI consumes their stable `checkoutUrl`, `code` and `error` contract; fixtures verify that compatibility. Real StoreKit/Swift shell behavior, RevenueCat restore/transfer configuration and sandbox purchase delivery, native installation and store approval remain unverified external/device gates. Pending markers last for the current browser/native webview session; a process that discards sessionStorage is not claimed to retain them. Provider SDK promises that do not settle still require native-runtime testing; the Swift bridge and HTTP refresh paths have explicit timeout recovery. The shell in-flight fence uses localStorage independently of account pending markers and does not expire merely because a page or process restarts. A native process that never delivers the matching callback needs verified native-side recovery before billing can safely resume; HTTP plan checks remain available. Real SDK multi-WebView serialization and process-loss recovery are not established by these fixtures.

Actual owning repositories currently lack the required write/workflow access, and an external writer was observed reverting reviewed hosted auth source. Root owns those release blockers and selective backend recovery. Do not call the billing product or entire suite ready based on this local client batch.
